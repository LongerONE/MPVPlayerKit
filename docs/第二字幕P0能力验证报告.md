# 第二字幕 P0 能力验证报告

日期：2026-10-15。范围仅 P0；未接入双字幕产品 UI、业务或 P1–P6。

## 结论

**No-Go：当前不能进入 P1–P6。** 已实际证明 MPVKit 1.0.0 的原生两路字幕字体、字号、文字色、描边及阴影共享，无法满足已确认的独立设置要求。第二路位置、延迟、显隐在本次文本渲染实验中独立。定制 mpv 候选补丁尚未编译和运行，不能据此宣称解决了共享样式问题；服务器图片字幕交付也未通过真实资源验证。

这不是判定定制方案不可实现，而是 P0 门槛尚未通过。报告交付完成不等于能力验证全部通过。

## 3. 双路实际渲染实验

`probe.c` 编译与运行均退出 0。原生主路样式属性存在；`secondary-sub-font`、`secondary-sub-font-size`、`secondary-sub-color`、`secondary-sub-border-size`、`secondary-sub-shadow-offset` 读取返回 `-8`（属性不存在）。第二路位置、延迟和显隐均可写回读，第一路位置/延迟不随之改变。

`render.c` 使用 `MPV_RENDER_API_TYPE_SW` 渲染为 RGB，输出 PPM。两路分别选择 sid=1、secondary-sid=2，字幕事件从第 1 秒到第 8 秒，播放定位第 2 秒、暂停。两路 ASS override 均为 force，以测播放器样式；第一路在底部、第二路在顶部。每次设置后处理事件，再渲染并比较上下半屏逐像素变化。

双 SRT 的实测相邻画面差异如下；上半屏为第二字幕，下半屏为第一字幕。

| 改动 | 第二字幕变化像素 | 第一字幕变化像素 | 判定 |
|---|---:|---:|---|
| sub-font → Courier | 1416 | 1229 | 共享，串路 |
| sub-font-size → 62 | 2578 | 2369 | 共享，串路 |
| sub-color → 绿色 | 2013 | 1761 | 共享，串路 |
| sub-border-size → 5 | 4169 | 3694 | 共享，串路 |
| sub-border-color → 洋红 | 4169 | 3694 | 共享，串路 |

随后把第二路延迟恢复 0，确认恢复显示，再隐藏第二路；对应帧及分析保存在同目录。描边和阴影初次使用黑色时在黑底不可见，已改为可见颜色重新运行，表中为最终复测值。没有把“属性设置成功”当作视觉效果成立。

最小复跑（先将脚本第一个命令的缓存路径替换为获授权的本机路径）：

```sh

python3 -I p0-scripts/run_render.py <p0-results>
```

**候选没有应用到产品、没有编译、没有运行，不是可用补丁。** 尚未证明变更通知、字体重配置、原始 ASS、位图、其他共享缩放/边距策略和各 Apple 架构完整性。

实际进行源码配置：

```sh
PATH=<p0-tools/bin>:$PATH PKG_CONFIG_PATH=/opt/homebrew/lib/pkgconfig \
  <p0-tools/bin/python3> -I -m mesonbuild.mesonmain setup --wipe \
  <p0-build> <mpv精确源码目录> \
```

首次因 pkg-config 路径未设置找不到 FFmpeg，修正后找到 libavcodec 62.28.102、libavformat 62.12.102 等。最终 **退出 1：缺少必需 libplacebo 开发依赖**；本机也未安装 libass 的 pkg-config 元数据。缓存 XCFramework 是静态产物，不能直接当作标准 Meson 开发环境。证据为 [meson-log.txt](../../.planning/2026-10-15-mpv-secondary-subtitle-design/p0-build/meson-logs/meson-log.txt)。

本轮有界验证未继续安装整套图形/字体依赖或执行完整 MPVKit 跨平台流水线。下一步需先准备可复现开发依赖，再编译候选、重复相同像素实验；未满足前不推进业务接线。

## 6. Temby 服务器只读核查

实际 GET 公开 `/System/Info/Public`、`/openapi.json`、`/swagger.json`，均 HTTP 200、curl 退出 0，确认 Emby Server 4.10.1.0。`GET /Items` 返回 HTTP 401。没有使用账号密码、没有创建登录会话、没有发送播放进度/设置/转码/字幕删除等写请求；报告和实验脚本不含凭据。

独立字幕端点由该服务器自己的公开 OpenAPI 确认存在：

`GET/HEAD /Videos/{Id}/{MediaSourceId}/Subtitles/{Index}/Stream.{Format}`，以及对应 Items 和 StartPositionTicks 路由。需要用户认证；`Format` 只是 string，没有枚举；成功响应为 “Response content unknown”。因此只能确认路由契约，**不能证明该版本能将 PGS/SUP 或 VobSub 成对资源完整交付**。本轮没有有效只读凭证和具体媒体/流索引，不能测试字节、MIME、成对资源、mpv 解码或无烧录源。不能用随意构造 URL、端点存在或 HTTP 200 的 OpenAPI 文档当资源成功证据。

如需继续，应使用用户提供的现有只读凭证及合法样本标识执行资源 GET/HEAD；当前授权禁止远程写状态，登录认证会创建服务器会话，故未执行。资源请求可能触发服务器提取/缓存，后续应先明确允许的只读资源访问范围。

延迟方面，实际 OpenAPI 的 PlayerStateInfo、PlaybackStartInfo、PlaybackProgressInfo 均有 `SubtitleOffset: integer/int32`；没有单位、正负方向或两路身份定义。UserItemDataDto 未提供字幕延迟字段，UserConfiguration 的 RememberSubtitleSelections 仅为布尔值。未找到满足“当前用户+媒体+具体字幕来源、跨会话读写、两路独立”条件的持久契约。该结论是**未证实支持**，不是断言所有 Emby/Jellyfin 版本都没有能力。

官方公开参考页也已实际取得 HTTP 200，见 [播放进度契约](../../.planning/2026-10-15-mpv-secondary-subtitle-design/p0-downloads/emby-progress/response)、[PlayerStateInfo](../../.planning/2026-10-15-mpv-secondary-subtitle-design/p0-downloads/emby-state/response)。本轮未实际访问 Jellyfin 实例，不为其作运行结论。

重新核对当前 Temby 源码：CacheManager.swift 仍以 subtitle_delay_tenths MMKV 长期读写；MyVideoPlayerView+Subtitles.swift 仍读取该值；PlayState.swift 有 SubtitleOffset，但当前 APIManager+Requests.swift 进度请求没有对应 offset 参数。全部仅核查，未修改。
